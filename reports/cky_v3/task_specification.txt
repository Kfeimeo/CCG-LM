# 一、项目背景

项目已有以下 CKY 实现：

- `reference`：最初的 CKY。
- `score_first`：V2，先进行标量结构筛选，再 Gather 高维向量。
- `lazy_semantic`：V2.5，先执行 Score-only CKY，再只对最终根候选需要的 DAG 节点执行 Composer。

已有实验还包含：

- V2.5-P：Composer 精度实验。
- V2.5-R：Semantic Reader 精度隔离实验。

目前已得到的结论：

1. V2 显著减少高维候选物化。
2. V2.5 将主模型 Composer Rows 从 43,072 降至 866。
3. V2.5 的主要速度收益来自减少语义 Autograd Graph。
4. 当前 CKY 的主要剩余瓶颈是标量搜索阶段的 Python 循环、频繁索引、Stack、GPU Kernel Launch 和反向梯度累积。
5. FP32 IEEE Composer 能使 V2/V2.5 的根语义结果在 FP32 计算下高度一致。
6. FP32 Reader 仅有限改善完整 BF16 梯度一致性，因此暂时保留 BF16 Reader。
7. 不应为了追求逐位 BF16 梯度相同而改变模型架构。

本次 V3 应集中优化剩余的结构搜索。

# 二、V3 核心目标

当前 Score-only CKY 大致采用：

```python
for width in range(2, max_words + 1):
    for start in range(num_spans):
        for split in range(start + 1, end):

            left_cell = chart[(start, split)]
            right_cell = chart[(split, end)]

            # 取出标量分数和 mask
            # 展开左右候选配对
            # 计算候选分数
            # stack / cat / select
            # Top-R / Exploration / Top-K
            # 写入 Python Cell
```

目标改成：

```python
for width in range(2, max_words + 1):

    # 当前 Width 的全部 Batch、历史句子和父 Span
    # 一起进行 GPU 标量候选计算

    left_scores = gather_width_left_scores(...)
    right_scores = gather_width_right_scores(...)

    candidate_scores = (
        left_scores + right_scores
    ) + parent_local_scores

    # GPU batched selection
    selected = batched_candidate_selection(...)

    # 保存当前 Width 的分数、Mask、Backpointer
    width_chart = ...
```

原则：

**可以保留跨 Width 的顺序循环，但尽量消除同一 Width 内逐 Span、逐 Split 的 Python 控制流。**

不允许为了减少循环而改变搜索候选集合或剪枝结果。

# 四、阶段 B：设计 Tensorized Score Chart

建议将 Batch 与历史句子维度合并：

\[
B'=B\times H
\]

对当前 Width \(w\)，父 Span 的起点数量为：

\[
N_w=n-w+1
\]

构建逻辑上的 Score Tensor：

\[
S_w\in\mathbb R^{B'\times N_w\times K}
\]

其中保存该 Width 每个父 Span 的最多 K 个保留候选分数。

另外保存：

```text
score
candidate_mask
candidate_id
left_candidate_id
right_candidate_id
split_index
source_metadata
```

可以使用按 Width 分开的 Tensor 列表：

```python
scores_by_width[w]
masks_by_width[w]
backpointers_by_width[w]
```

或紧凑的 Packed Chart Layout。

实际张量布局由性能测试确定。

## 4.1 优先采用按 Width 分层保存

不要求将全部 Chart 写成一个巨大的 Dense Tensor。

可以按 Width 保存不同形状：

```text
width=1: [B', n, K]
width=2: [B', n-1, K]
width=3: [B', n-2, K]
...
width=n: [B', 1, K]
```

不同 Width 可以通过预计算的索引表读取依赖。

这种设计需要保证：

- 每一层只依赖已经完成的更短 Width；
- 不覆盖尚需参与 Backward 的值；
- 不破坏 Autograd Version Counter；
- 不错误地重复计算同一 Span；
- 不使用 detach 切断 Span Score 梯度。

## 4.2 不要直接进行危险的 In-place Chart 更新

禁止使用会静默截断梯度的模式，例如：

```python
chart = torch.zeros(...)

chart[index] = score.detach()
```

也不能假设把有梯度 Tensor 写入普通预分配数组后，所有后续梯度一定正确。

允许：

- 函数式张量更新；
- 可微分 `gather` / `index_select`；
- 按 Width 保存新的 Score Tensor；
- 经过验证的可微分 Scatter；
- 将不可微的 Candidate ID、Mask 与可微 Score 分开管理。

必须使用实际 Backward 测试证明梯度完整。

# 五、阶段 C：GPU Wavefront Candidate Scoring

对每个父 Span：

\[
[i,j),\qquad j=i+w
\]

合法切分：

\[
i<k<j
\]

左右候选分数：

\[
\ell_L^{(p)},\quad \ell_R^{(q)}
\]

父候选分数：

\[
\ell_P
=
(\ell_L^{(p)}+\ell_R^{(q)})
+s_{i:j}
\]

要求维持原 V2.5 的加法顺序。

对当前 Width，在 GPU 上形成逻辑上的候选张量：

\[
Q_w\in
\mathbb R^{
B'\times N_w\times(w-1)\times K\times K
}
\]

然后处理有效候选 Mask。

这里的 K×K 是**张量化上界**，不代表所有槽位均有效。

## 5.1 正确处理 Ragged Beam

当前 V2.5 的候选配对排列，可能根据左右 Cell 的实际槽数变化。

例如某个 Split：

```text
left slots = 2
right slots = 4
```

有效配对只有 8 个，而不是 16 个。

另一个 Split 可能是：

```text
left slots = 1
right slots = 2
```

有效配对只有 2 个。

必须保留原实现中的：

```text
(offset, left_slot, right_slot)
```

以及对应的候选 Flat Identity。

如果使用固定 K² Dense Tensor，应建立明确的：

```text
dense_pair_index → legacy_flat_index
```

映射。

非法 Padding 候选不能改变有效候选的相对顺序。

禁止仅使用固定：

```python
flat_id = split * K * K + left * K + right
```

替代原始 Ragged Layout，除非已经证明二者对所有配置等价。

候选身份与 Backpointer 必须经过专门测试。

## 5.2 Mask 与不可达处理

应处理：

- 无效历史句子。
- Padding 词。
- 未满 K 的 Beam。
- 不可达 Span。
- 负无穷结构势。
- 无效左右子候选。
- 没有任何有效 Split 的父 Span。

不能将全 `-inf` 的候选交给不安全的 Softmax 或其他操作而产生 NaN。

不能为不可达 Span 制造伪合法候选。

## 5.3 保持数值加法顺序

已有精度实验发现：当前叶子分数与内部 CKY 分数可能使用不同 dtype，第一次相加前后的 Cast 位置会影响候选选择。

因此，本次 V3：

**必须保留旧 V2.5 的实际 dtype、加法次序和转换时机。**

不要顺便把所有 Score 改为 FP32。

如果新的批量化路径使 FP32 与 BF16 运算顺序发生变化，需要单独报告。

调整 Score Precision 应作为后续独立实验，而非 V3 的隐含改动。

# 六、阶段 D：GPU Batched Top-R / Top-K

这是 V3 最关键、也最容易引入搜索变化的部分。

现有搜索顺序需要原样保留：

```text
候选 Score
    ↓
Top-R / Proposal Budget
    ↓
预算内随机探索
    ↓
Top-K
    ↓
Beam Exploration Replacement
    ↓
Delta Pruning
    ↓
写入保留候选
```

以实际源码的最终执行次序为准。

## 6.1 批量选择

尽量将同 Width 所有父 Span 的候选组织为：

```text
[B', N_w, candidate_capacity]
```

使用 GPU Tensor 批量执行 Top-R 和 Top-K。

不允许将每个父 Span 的分数：

```python
scores.cpu().tolist()
```

再交给 Python 排序。

## 6.2 严格保留同分处理

`torch.topk` 对完全同分的候选，可能因为 Tensor Shape、Stride 或 Kernel 选择不同而返回不同索引。

本次必须专门验证：

- 完全同分。
- 近似同分。
- 所有候选相同。
- 不足 R 个候选。
- 不足 K 个候选。
- 含无效槽位。

如果新的 Batched Top-K 与原单 Span Top-K 在同分场景下不同，不允许简单称为无关差异。

可以探索以下兼容方案：

1. 保留与旧实现一致的候选排列。
2. 对相同形状验证原生 Top-K 是否保持相同选择。
3. 如果确有必要，对少量特殊场景使用 Legacy Selection Fallback。

不要擅自新增基于 Candidate ID 的排序规则，因为这可能改变原模型的同分候选行为。

如严格等价不可实现，应将相关测试标记为明确的 No-Go，而不是放宽测试。

## 6.3 保持随机探索分布与 RNG

当前 V2.5 的随机探索已在历史实验中验证与 V2 一致。

Tensorized CKY 可能改变随机数生成次序。

必须检查：

- Python RNG。
- NumPy RNG。
- PyTorch CPU RNG。
- PyTorch CUDA RNG。
- 探索采样操作的调用顺序。
- 不同有效候选数量对应的采样次数。

优先实现与旧 V2.5 相同的随机行为。

如果无法完全向量化且保持相同 RNG：

- 可以先仅将 Score Pairing Tensorized；
- 暂时保留 Legacy Exploration 的兼容路径；
- 不能以替换探索分布换取加速；
- 必须报告该路径残留的 Python 开销。

可设计仅用于验证的 Exploration RNG Replay，但不得把重放旧实现的随机结果作为正式训练时不可缺少的运行条件。

不要为了追求性能而改变训练算法。

# 七、阶段 E：可微 Score 与 Autograd

这是 V3 的硬性验收条件。

当前 V2.5 使用可微累计结构分数：

\[
\ell_P=\ell_L+\ell_R+s_{i:j}
\]

在根候选归一化后：

\[
\log\pi_k
=
\ell_k-\operatorname{logsumexp}_r(\ell_r)
\]

并通过 Semantic Reader 的 Log-Prior 路径反向传播到 Span Scorer。

V3 必须保持这一梯度路径。

## 7.1 第一阶段采用原有可微 Score Graph

首先实现：

```text
Width-batched Scoring
    ↓
可微 Tensor Score
    ↓
离散 Candidate Selection
    ↓
保留根 Score
    ↓
Log-Prior
    ↓
LM Loss
```

Top-K 的离散索引不可微是原模型已有性质，不需要改变。

但是被选中候选的分数必须继续具有 `grad_fn`。

## 7.2 可选的第二阶段：Score Graph Reconstruction

如果 V3 第一阶段通过正确性测试，但 Autograd Graph 仍然很大，可以单独实验：

```text
No-grad Score-only Search
    ↓
选定根候选 Backpointer
    ↓
按已选树重建可微累计 Score
    ↓
Log-Prior
```

此方案必须保持原搜索过程的前向 Score 精度和排序完全一致。

重建结构分数时，需要保留原始 Span Logit 的可微引用。

必须验证：

- 与现有 V2.5 相同的根分数；
- 相同的 Log-Prior；
- 相同的 FP32 梯度；
- 非零 Span Scorer 梯度；
- 不发生意外的梯度重复或遗漏。

**这一优化是可选的 V3-B，不得与基础 Width Tensorization 同时实施。**

若严格一致性失败，保留基础 V3-A。

# 八、阶段 F：结构索引缓存

CKY 的合法区间与切分索引仅依赖：

- 最大句长；
- Span Width；
- Chart Layout；
- K 上界；
- Device；
- Index Dtype。

因此可以预计算并缓存：

```text
left_cell_indices_by_width
right_cell_indices_by_width
parent_cell_indices_by_width
split_indices_by_width
structural_valid_masks
```

建议使用 GPU Long Tensor 缓存。

缓存要求：

1. 不包含任何可训练参数。
2. 不缓存 Syntax Encoder 输出。
3. 不缓存 Composer 输出。
4. 不跨 Optimizer Step 复用语义图。
5. 不错误地缓存动态可达性 Mask。
6. 缓存 Key 能区分设备、句长、布局和 K。
7. 不在每次 Forward 重建相同的 Python 索引表。

需要区分：

**静态几何索引可缓存，动态候选有效性不能简单缓存。**

允许按历史长度 Bucket 复用结构索引。

本次不要求重新设计 DataLoader，但 Benchmark 应包含固定句长与动态 Padding 两种情况。

2. Root Log-Prior 路径有效。
3. Composer 梯度没有改变拓扑。
4. DAG 共享梯度正确累计。
5. 无 In-place Autograd 错误。
6. 不出现 NaN / Inf。

旧实验已经发现某些公共 Span Score Bias 存在中性方向，AdamW 可能放大其浮点残差。

本次不修改或冻结这些参数。

BF16 差异继续按先前 V2.5-P/R 的方法报告，不强制要求不同批量计算路径逐位相同。

## 11.5 训练与 Checkpoint

至少执行：

- CPU FP32：8 个相同训练 Step。
- CUDA BF16：20 个相同训练 Step。
- 从旧 Lazy Checkpoint 显式切换到 V3 的恢复测试。
- V3 Checkpoint 保存和恢复后的重放测试。

应验证：

- 训练不会崩溃；
- 学习率及 Token 计数连续；
- RNG/Optimizer 恢复正确；
- 结构选择在固定权重时一致；
- 不出现梯度缺失。

训练轨迹因为数值舍入而分叉，不自动判定模型错误，但应完整记录。

# 十三、分阶段实施，避免一次重写过多

- 有效性 Mask。

- Delta。

完成严格一致性测试。

## V3-C：Autograd 与 Chart 整理

如果结构搜索 Backward 仍然过慢，优化：

- 不必要的 Score Tensor 复制。
- 重复 SelectBackward。
- 不必要的 Scatter/Stack。
- 函数式 Chart 更新。
- 对已经选定的根树进行可微 Score Reconstruction（可选）。

必须单独测试此阶段的数学与梯度等价性。

不允许同时改变多个核心机制后才进行一次总测试。
